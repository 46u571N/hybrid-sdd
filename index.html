01La analogía correcta

Spec Kit y OpenSpec no compiten por el mismo trabajo. Uno gobierna una vez; el otro trackea cada cambio, como un commit.

Una vez por proyecto

Constitution

Reglas no negociables: testing, estilo, seguridad. Se escribe una vez y todo lo que viene después la hereda.

.specify/memory/constitution.md
Por cada cambio

Delta de OpenSpec

Cada cambio es su propio "commit": solo documenta qué se agrega, modifica o elimina — no regenera el spec entero.

openspec/changes/<id>/

02El right-sizing, en vivo

Lo que cambia entre un cambio chico y uno de alto impacto no es el framework — es cuántos artefactos genera esta misma carpeta. Probalo:

Tipo de cambio en changes/<id>/
Proposal + tasks alcanza para la mayoría del trabajo diario — rápido y barato en tokens.

03Dónde entran nuestras convenciones

.ai/project-knowledge.md, pause/ y resume/ no son de ningún framework — son nuestras. Así quedan ubicadas:

<repo-raíz>/
├── .specify/
│   └── memory/
│       └── constitution.md        # Spec Kit — una vez por proyecto
├── .ai/
│   └── project-knowledge.md       # nuestro — cómo funciona el sistema hoy
├── openspec/
│   ├── specs/                     # OpenSpec — verdad vigente, por dominio
│   │   └── <dominio>/spec.md
│   └── changes/
│       └── <id>/
│           ├── proposal.md
│           ├── specs/              # delta de este cambio
│           ├── design.md           # + analyze, checklist si alto impacto
│           └── tasks.md
├── pause/
│   └── <id>.md                    # nuestro — estado congelado
└── resume/
    └── <id>.md                    # nuestro — instrucción de reanudación

Qué hacemos con esto

  1. Corto plazo: seguimos con nuestra skill de Claude como motor. Adoptamos el esqueleto specs/ + changes/<id>/ de OpenSpec como layout por defecto.
  2. El vocabulario pesado de Spec Kit (clarify, analyze, checklist) se reserva para cuando el right-sizing marque alto impacto — no para todo el trabajo diario.
  3. No instalamos los dos CLIs. Ninguno resuelve hoy un problema que no tengamos ya cubierto con la skill.
  4. Si alguien del equipo necesita trabajar sin Claude, ahí evaluamos instalar uno solo — según si el trabajo predominante es greenfield o iteración sobre producto existente.
